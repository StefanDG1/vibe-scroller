# Writing standard

Mode: reference.

Documentation uses plain language and exact technical names. Each file has a primary purpose: a procedure, reference, explanation, or tutorial. Procedures use imperative steps and visible outcomes. Reference documents state fields, states, and rules without promotional claims. Explanations describe trade-offs and the reason for a decision.

Keep claims specific. Name the actor, condition, action, and result. Preserve the difference between a verified integration, a design requirement, an assumption, and a release gate. Use sentence-case headings and readable paragraphs. Avoid em dashes, decorative emoji, repeated slogans, and generic conclusions.

Use the same term for the same concept: source, insight, match, proposal, plan, run, PR, and outcome. A source is not merged. A PR is merged. A user accepts a proposal. A user or measurement records benefit.

The product UI can be friendlier than a protocol reference, but it must not hide uncertainty or cost. "No useful match found" is better than an invented recommendation. "Waiting for your laptop" is better than a fake progress percentage.

Respect the two supplied writing skills without republishing their full contents or implying that their licence covers this application's other material.
