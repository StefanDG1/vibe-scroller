# Configure scoped assistant access

Mode: how-to. The current adapter remains disabled pending real account acceptance. Configuration and local tests do not establish a working ChatGPT connection.

Use the existing dedicated VibeScroll WorkOS environment and canonical resource `https://scroll.companynerve.com/mcp`. Preserve the ordinary application client, cookies, callbacks and existing authentication methods. The Connect client is separate from the app sign-in client.

1. Register an external assistant as a third-party OAuth application associated with its integration organization. Use public PKCE and the exact callback copied from that host's official connection screen. Do not suppress consent or guess a generic callback. Keep dynamic registration and client metadata registration off until their custom-scope behavior has separate verification.
2. Configure the canonical resource indicator in WorkOS. Register only implemented scopes: `knowledge:read`, `context:read`, `links:save`, `jobs:read`, `analysis:request`, `feedback:write` and, after deploying the private project adapter, `suggestions:draft`. Standard identity login does not grant any app knowledge access.
3. Prepare `MCP_AUTH_ISSUER` with the exact dedicated HTTPS AuthKit issuer, and `MCP_CLIENTS` with a JSON array of at most four objects containing the actual client `id`, display `name` and implemented `scopes`. Use encrypted provider configuration; retain `MCP_ENABLED=false` during preparation. Set matching registry and issuer values in the serving frontend and Convex environment. Preserve `NEXT_PUBLIC_CONVEX_URL` and `WORKOS_CLIENT_ID`; do not replace infrastructure or credentials.
4. Check protected-resource discovery, official issuer discovery and registered callbacks before a bounded private acceptance run. The public PKCE client uses no client secret. Each tool call sends its bearer only to the dedicated Convex HTTP endpoint and the exact issuer's official `POST /oauth2/userinfo`; only the matching subject is used from that response. JWT signature, resource audience, expiry, client and scopes remain independently verified. Live provider disconnection/revocation must be tested rather than inferred from this documented endpoint.
5. In Connections, review the client, permitted actions and exact current saved-post versions. Optionally select the current confirmed library goal/interests, up to five exact current project contexts, or a private intake space. Project choices have their own twenty-entry pages. Selecting a project does not include repository code. Private project suggestions require selected evidence, context read permission and owner/admin authority. Select at most 50 posts across 20-entry metadata pages, open their evidence and the selected list, then acknowledge the exact selection. App authentication must be no older than 300 seconds when saving. The interface grants seven days; the backend rejects expiry beyond 30 days. Replacing a grant removes prior authority. Neither consent nor a grant authorizes processing, coding or publication.
6. Complete the host's own risk acknowledgment and official OAuth consent. Verify a cited read, explicit permitted link save, canonical replay, own-record export, changed evidence, foreign account/workspace denial, revoked app grant and revoked provider connection. Keep tokens/codes out of messages, logs, databases, recordings and fixtures. Pause only the dependent check when a fresh owner step is unavailable.
7. Record exact frontend/backend commit, domain/version, provider/client and UTC receipts in implementation status. Enable broader access only after the actual account journey passes. Revoke access immediately in Connections; already disclosed host conversation content cannot be retracted by future retrieval revocation.

## Tool limits and recovery

Search checks up to five selected source records and returns up to 20 clipped matching ideas per page. Fetch returns one current selected idea or up to 20 ideas and ten evidence timestamps each. Citations open protected app pages. Neither tool returns original transcripts, media, signed assets, credentials or chat history. An incomplete result page does not establish absence or no-fit.

Explicit intake reuses safe source URLs, rights, quotas and deduplication. It suppresses link previews, downloads and model work. Newly saved links need separate review before retrieval. Status can cover exact selected work or an intake receipt bound to the same grant version. Analysis requests return the existing app approval link without spending or reserving credits.

The adapter limits requests to 30 per actor/client per rate window. Request bodies and provider responses have byte limits and timeouts. Authentication failure requires official reconnection; app authorization failure requires review of the current grant/evidence. A temporary dispatch/configuration failure returns unavailable instead of an authentication challenge. Retry conservatively with the original intake key after an uncertain response. Never retry by widening scopes or selecting a paid provider.

Current tools are `search`, `fetch`, `get_profile`, `save_link`, `get_job_status`, `request_analysis`, `record_feedback` and `draft_project_suggestion`. Feedback requires its separate registered scope, exact source/grant versions and expected correction version. Project drafts require both `context:read` and `suggestions:draft`, an explicit request, exact evaluation hash and grant version. Use `get_profile(profileId)` to discover current approved project context and evaluation metadata; default discovery pages ten profiles and omits full project context. The draft tool reuses the existing private cited issue workflow, preserves manual edits on retry and returns distinct non-fit judgments without creating a draft. It starts no new inference, spending, publication or coding. Real host invocation still requires acceptance. Persistent signed Events delivery and actual supported-host completion remain separate; an in-process SDK event bus does not establish that delivery. Optional widgets, public plugin distribution and general hosted subscription inference remain gated under their existing contracts.

## Prepare persistent completion Events

The implementation uses the actual SDK's typed custom handlers for the modern `2026-07-28` transport. `events/list`, `events/subscribe` and `events/unsubscribe` appear only when `MCP_EVENTS_ENABLED=true`. Keep that flag off pending supported-host acceptance and verified provider revocation. The in-process `subscriptions/listen` bus remains unsupported.

After the verified backend/frontend adapter is deployed, register `events:subscribe` for the actual third-party application and update only its private prepared registry. Configure a new dedicated 32-byte base64 `MCP_EVENT_SECRET_KEY_1` on frontend and backend, plus `MCP_EVENT_SECRET_KEY_VERSION=1`. Never reuse a local subscription credential, provider key or backup key. Keep key versions available only while their at-most-thirty-minute subscriptions and short rotation overlap survive. Do not put values into source, logs, screenshots or consent messages.

Select an exact profile/source generation/current app-grant version. The host provides its actual HTTPS callback and `whsec_` signing secret; the frontend seals those with the verified Connect bearer before internal dispatch. No authorization or MFA code is stored. Verify a fresh signed challenge before activation, or reuse verification for at most five minutes with the same principal/callback/secret. Subscription identity includes canonical filter fields and callback. `refreshBefore` is the granted finite expiration, bounded by thirty minutes, token expiry and app-grant expiry; `ttlMs:null` still receives finite authority. No cursor replay is promised.

The existing atomic source completion mutation inserts a minimal outbox receipt and schedules durable delivery. Retries preserve event ID/body and refresh signing time, with a maximum of five attempts. A one-minute bounded recovery repairs interrupted leases. Normal delivery reads the HTTP status and closes the irrelevant response body; verification challenges still read a bounded matching body. A 2xx records HTTP receipt only; it does not establish that ChatGPT processed or displayed the event. A 410/413 stops delivery. Current JWT/provider authorization, grant, membership, workspace, source rights and generation are checked before transmission. App-grant changes invalidate subscriptions. Account/workspace deletion and restore quarantine include the new records.

Run the actual host lifecycle before activation: modern discovery, scoped consent, callback challenge, completion after UI closes, nonmatching filter, duplicate/retry, secret rotation, restart refresh, expiry, unsubscribe, disconnect and resource revocation. Inspect the actual host's response, not a synthetic callback. The owner must approve its concrete final consent screen; configured scopes cannot provide that approval in advance. See [ADR 088](../adr/088-persistent-scoped-completion-events.md).
