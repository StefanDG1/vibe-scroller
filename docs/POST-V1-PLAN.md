# VibeScroller plan after V1

Mode: reference. Planning baseline: October 3, 2026. Status: proposed, reviewed against the repository. Application implementation, recruitment, publication and spending are not authorized by this planning document.

The next milestone is independent use. A new person can operate the public-source version from its documentation. A hosted customer can obtain a useful result without founder assistance. Several customers return because the workflow helps their projects. These outcomes precede broad acquisition or proprietary V2 implementation.

## Current baseline

The [readiness record](V1-READINESS.md) and [production release record](operations/paid-release-2026-10-03.md) describe enabled features and precise limits. Production application commit 2e3c02f4f8b5721f4c3127f351a46fef76e34310 has automatic analysis, library organization, approved isolated coding, draft PR tracking and live Managed Payments evidence. Later documentation commits do not replace that application build.

The remaining V1 acceptance work includes numerical evaluation, provider-cost reconciliation and full recovery cutover rehearsal. Forty owned synthetic clips and one licensed human excerpt completed 41 analyses and 82 comparisons. The original 23 examples and five real posts have qualitative owner acceptance. Numerical human review remains zero in the retained [collection record](../infra/completed-owned-quality-observations-20261003.json). Existing clips are predominantly synthetic; this is not representative customer-quality evidence.

The existing README, documentation index and local-development guide contain inherited CompanyNerve instructions or older availability claims. V1-authored source is MIT, but supported independent setup remains deferred by D16. Source publication does not establish that a stranger can install and operate the product.

## Sequence and dependencies

The timing below is a planning range. Provider billing periods, human review, recruitment and account approvals can extend it. An engineer is responsible for implementation and evidence. The founder owns product decisions, recruitment and publication approval. A human reviewer scores quality; no agent can manufacture those annotations.

| Phase                        | Indicative window after implementation authorization  | Deliverables                                                    | Exit decision                                                                               |
| ---------------------------- | ----------------------------------------------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| A. Complete V1 acceptance    | Weeks 1 to 2; invoice evidence may arrive later       | P01 quality, P02 costs, P03 recovery, P04 current documentation | Precise closure of applicable V1 criteria, or named unresolved evidence with limited claims |
| B. Establish independent use | Weeks 2 to 3, with documentation preparation during A | P05 independent setup, P06 usability, P07 measurement           | Fresh users complete the supported workflow without founder intervention                    |
| C. Validate recurring value  | At least four weeks of actual cohort observation      | P08 small cohort, P09 paid-service validation                   | Continue, revise the offer, or narrow the audience from observed results                    |
| D. Improve and demonstrate   | During and after C, one product improvement at a time | P10 selected V1.1 work, P11 demonstrations and tutorials        | A measured improvement or an explicit unsuccessful experiment                               |
| E. Expand deliberately       | After C and D evidence                                | P12 broader distribution, P13 V2 decision                       | Enough recurring value and operating capacity to justify expansion                          |

Phase A documentation and Phase B research preparation do not require a numerical-quality claim. A usability study or private setup test can proceed with explicit limits. Broad marketing, reliability claims and scaling depend on the relevant acceptance, capacity and outcome evidence. An unmet phase does not silently become a completed release.

## A. Complete V1 acceptance

### P01. Finish the numerical quality report

Owner: engineer and human reviewer. Dependencies: existing rights manifests and retained outputs. Priority: required V1 validation.

Deliverables include a frozen dataset/model/prompt/commit manifest, human score sheets and a public aggregate report. Scores cover evidence-supported main points, useful timestamps, speech error rate, technical-name accuracy, invented file/API claims, project-match precision and correct abstention. Existing qualitative approvals remain qualitative.

The review starts with retained outputs, so completing annotations does not require reprocessing all clips. Cases used to tune the pipeline are development cases. The nominal held-out split is audited because fixes occurred during collection. Any new comparative claim uses a frozen evaluation subset whose answers did not guide that change. More rights-cleared human speech is added only when necessary for a stated coverage question and approved budget.

Variants of the same authored scenario belong to the same split. The report distinguishes clip count from independent scenario count. Evidence support means correspondence to the source, not proof that a creator's advice is true. The rubric distinguishes faithful reporting, supported inference, contradictory evidence and invented claims.

The suggested target from [feedback and evaluation](FEEDBACK-AND-EVALUATION.md) remains zero critical invented claims and at least 90 percent human-supported main points on the held-out sample. Counts, denominators and coverage limits accompany every result. A small or unrepresentative sample cannot establish population accuracy. Failure leads to a scoped pipeline fix and a new held-out evaluation, not altered reference answers.

Acceptance: all required categories and both repository profiles have explicit references, reviewer identities and scores. Missing annotations remain missing. `pnpm benchmark` emits a valid report. Its exit 2 remains an incomplete or below-target result; exit 1 is invalid input/output. The exact code, source rights, commands and limitations are retained.

Quality closure requires the selected complete held-out report to meet the suggested target, or a recorded review that restricts unsupported claims and keeps the applicable criterion unresolved. Provider-cost closure is separate. The evaluator can return exit 0 with unknown settled costs, so that exit cannot pass P02 or the cost portion of AC53.

### P02. Reconcile costs and operating capacity

Owner: engineer, with founder access to provider reports. Dependencies: actual usage records and current provider tariffs. Priority: required V1 validation and cohort capacity.

The cost record joins job IDs to model usage, sandbox runtime, failed/retried attempts, storage/egress and the applicable billing period. Costs distinguish attributable variable usage, allocated shared costs, gross usage before credits and actual cash charges after credits. An included allowance is not proof that a workload has zero economic cost.

The financial model includes payment/Billing fees, Managed Payments on its actual fee basis, approved Radar screening, refunds and FX. Annual full-use and high-cost cases remain visible. Settled provider currency and the documented FX date reconcile to app settlement and quotes. Charges that cannot be assigned to a job remain an explicit unattributed amount.

Acceptance: each observed workload has a settled, pending or unattributed cost status. Actual invoices or authoritative provider billing exports reconcile to the billing period; delayed invoices remain pending. The owner-defined 60 percent operating-margin target is reported using its existing exclusions and is not renamed as all-in profit. Quotes reserve bounded exposure for failures and teardown. No budget ceiling changes occur as part of measurement.

Before cohort admission, forecast the authorized workload against remaining inference, service and sandbox headroom. Trial restrictions or an exhausted ceiling stop new work. A capacity increase requires an owner decision supported by this record.

### P03. Rehearse complete recovery without changing production

Owner: engineer. Dependencies: backup access, deletion markers and a newly created isolated destination. Priority: required V1 validation.

The previous temporary recovery deployment was deleted and cannot be reused. The rehearsal uses a fresh locked destination, current compatible schema and explicitly selected backup versions. It restores the application and relevant component tables, then retained objects or an explicit unavailable-object state. Newer deletion markers apply before any serving access. Stale approvals, provider cursors, unknown costs and credential bindings are reconciled or quarantined.

Acceptance: the recovery application serves an authorized test identity from a separate test hostname while denying foreign access. Deleted sources remain inaccessible. No recovered job, email, payment or PR dispatches accidentally. An interruption and rollback preserve the selected recovered state. Measured recovery time and data-loss window come from the exercise, not invented service promises. Cleanup removes plaintext and the temporary destination. Production DNS and live routing stay unchanged.

A production traffic cutover, if later needed, requires its own reviewed operational decision. This plan does not authorize a destructive failover.

### P04. Align current documentation and release evidence

Owner: engineer. Dependencies: current product behavior. Priority: first documentation work.

The proposed documentation map gives separate paths to hosted users, personal deployers, contributors and operators. README and `docs/README.md` stop describing the repository primarily as the CompanyNerve starter. `docs/local-development.md` uses actual VibeScroller onboarding, prices, webhook routes and provider configuration. The original handoff remains preserved as provenance.

Deliverables include a supported-capability matrix, known limits, a short hosted tutorial, current personal setup, contributor guidance, a security-reporting route, troubleshooting and an operator runbook. Existing documents are reused or corrected before adding duplicates. Each release has one current readiness record with links to historical evidence.

Acceptance: all links and example commands validate. A fresh reader can distinguish demonstrated data, customer data, personal funding, managed funding and unavailable routes. No guide inherits founder credentials or requires live Stripe for ordinary personal use. Documentation-only updates use the existing build-skip policy.

## B. Establish independent use

### P05. Support one personal deployment path

Owner: engineer, with two fresh external testers. Dependencies: P04 and an explicit follow-on scope decision for D16.

The first supported path keeps the selected stack. It is a user-operated deployment using that user's provider accounts. It is not advertised as an entirely local or fully self-contained installation. The provider matrix identifies which services are needed for library, analysis, GitHub and optional hosted coding. Billing and operator analytics are optional when they are not needed for the selected personal path.

The setup design has one documented package install, environment validation and preflight checks. It includes a clearly labeled demo requiring no live provider configuration, followed by a real account-backed workflow. Any setup helper performs scoped operations only after the user understands the connection. Sample configuration contains no keys, production identifiers or customer data. Supported OS and funding combinations come from tests; Windows local coding stays disabled until its boundary passes.

Acceptance: two testers using clean checkouts and their own accounts complete setup, import a permitted source, obtain a cited analysis, export their work and understand the coding options without private founder instructions. Provider prerequisites, active setup time, approval waits and billed resources are recorded separately. At least one tester performs an upgrade and verifies retained data. Setup-time targets follow this first baseline instead of promising a ten-minute installation now.

Public-source success is measured by successful independent setups and repeat use, with consented reports or voluntary feedback. Clone counts and stars alone do not pass this package. Users receive no compulsory telemetry.

### P06. Observe and improve first use

Owner: founder and engineer. Dependencies: P04; P05 applies to the personal cohort.

The usability exercise separates hosted customers from technical personal deployers. Hosted participants start with their own account and one permitted link, without GitHub connection being required for the first library result. Participants find an insight, retrieve it again, then optionally connect a project and review a plan. The observer records prompts and help rather than disguising an assisted success as independent completion.

The exercise covers empty, loading, success, error and unavailable states, including an offline paired laptop and exhausted allowance. Recovery actions preserve the user's input. No uncertain write result invites repeated blind submissions. Mobile tests include the owner's physical Android when available; screenshots and Chrome widths remain a separate evidence class.

Acceptance: after fixes, at least four of five fresh hosted participants complete import and insight retrieval without observer intervention. A separate group can find and understand a relevant plan or correct no-fit result. This is a proposed small-pilot usability gate, not a population conversion claim. Critical access, billing or isolation defects require the affected route to pause. Keyboard, focus, reduced motion, touch targets and long text remain regression checks.

### P07. Measure the two user journeys

Owner: engineer and founder. Dependencies: existing consent controls and P04 definitions.

The event audit maps existing events before adding names. It checks capture, processing, analysis view, explicit usefulness, repository connection, proposal review, plan approval, authorized run, draft PR, verified merge, benefit feedback, checkout and payment reconciliation. Anonymous marketing and authenticated product measurements retain their consent rules. Sensitive URLs, transcript text, images, private code and credentials never enter analytics properties. Provider completion and payment facts come from the authoritative backend, not browser clicks alone.

Two activation measures remain separate. Library activation is a completed source whose analysis the person opens. Project activation is an explicit relevance review followed by a saved plan, manual handoff or documented no-action decision. A correctly rejected suggestion can be useful. Merge remains distinct from benefit.

Acceptance: consented test events appear once with the right identity and workspace. Opt-out prevents optional capture; logout/workspace switch does not expose the previous identity. A no-consent user can use the product. Duplicate webhook deliveries do not inflate payment or PR counts. Operational/security records needed for the service have their separate retention and purpose, not an invented analytics-consent exception.

## C. Validate recurring value

### P08. Run a small observed cohort

Owner: founder. Engineer resolves defects. Dependencies: P06, P07 and reviewed capacity from P02.

Rolling admission starts with three users during the usability phase. Admission expands toward 10 to 15 only when support and processing capacity allow. Consenting usability participants can continue into the cohort. Each person is counted once, and assisted sessions are marked. The four-week observation starts from that person's recorded activation, with product versions and interventions visible. Growth waits for the P06 usability result and P07 measurement checks.

Participants have a recent practical source, an active project and permission to submit both. Recruitment messages and posts require explicit authorization before sending. Reports use permitted aggregate observations; private media and code are not marketing assets.

The four-week observation records the participant's current workflow, first useful result, correction burden, processing failures, voluntary return, explicit decisions and reasons for leaving. A small matched comparison uses a manual workflow on comparable tasks; assistance, task difficulty and model-route differences remain visible. Self-reported savings stay labeled self-reported.

Acceptance: the cohort report includes every enrolled participant and every unavailable or unreviewed outcome. The proposed next-stage target is five of the first ten activated users returning in a later week and explicitly identifying repeat value. This target is a decision aid, not proof of product-market fit. If the cohort is too small or the result weak, another feature or advertising launch is not the automatic response. The next action is a narrower problem, a revised onboarding experiment or a candid stop decision.

### P09. Validate the paid offer

Owner: founder, with engineer cost evidence. Dependencies: P02 and observed cohort value.

The hosted offer explains service access, analysis allowance, compute costs and optional personal funding separately. Existing Starter/Pro prices are tested through genuine buyer behavior before adding tiers or changing allowances. A useful library-only user can be a customer, but that validates a different value proposition from coding.

The initial target is three to five independent paying customers who state their reason for buying. Retention is observed for at least one applicable renewal opportunity; a prepaid annual purchase is not evidence of a renewal. Free testers, the founder and friends making a purchase only to help are not counted as independent demand evidence.

No founder live purchase, forced refund or manufactured transaction is required. Actual voluntary customer transactions can be inspected for entitlement, settlement and accountant handover. Sandbox remains the controlled billing test environment.

Acceptance: payments reconcile to access, credit grants and actual fees. Cancellation, export and account rights remain understandable. The report includes decline reasons, support effort and full-use margin pressure. If contribution is inadequate, quote limits, scope or price are reviewed before acquisition grows. Any customer-facing price, funding or allowance change needs its own owner decision and existing-customer treatment.

## D. Select V1.1 work and create proof

### P10. Ship one demonstrated friction fix at a time

Owner: engineer and founder. Dependencies: a repeated observed problem, cost bounds and a named acceptance test.

| Candidate                    | Initial scope                                                                      | Release evidence                                                                                                                              |
| ---------------------------- | ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Android capture              | Installed PWA share target for supported URL/text input, with paste fallback       | Real phone share/import, duplicate handling, offline/offline-runner status, logout and workspace cache isolation                              |
| Library questions            | Read-only answers citing source/insight/evidence IDs from the active workspace     | Known-answer and no-answer evaluation, foreign-workspace denial, deletion enforcement, explicit funded query limit; no model-triggered coding |
| Weekly review                | In-app digest first; email/browser notification only with channel permission       | Useful/deferred/duplicate grouping, bounded frequency, opt-out and no private lock-screen text; notifications never authorize work            |
| Source retrieval reliability | Clear retry policy and approved thumbnail/media adapters for demonstrated failures | Actual supported public-link regression sample, explicit private/deleted/blocked states, rights and platform-policy checks                    |
| Repository compatibility     | An additional observed dependency/manager combination in the isolated cache        | Actual checks, malicious-project isolation, quote/teardown bounds and trusted publication; no unrestricted install fallback                   |
| More transcription coverage  | Language or accent coverage demanded by the cohort                                 | Rights-cleared human samples and separate accuracy/cost report for that route                                                                 |

Selection weighs affected users, severity, expected usefulness, effort, recurring cost and permission risk. The order above is an initial proposal, not a commitment to ship all candidates. A fix that prevents lost imports takes priority over a conversational feature when evidence supports it.

Acceptance: the selected change improves the stated measure on a comparable cohort or test set without weakening critical boundaries. The other candidates remain backlog. General autonomous execution, cross-customer training and fine-tuning are excluded. Shared category vocabulary remains content-free, optional and reviewed; private customer feedback does not become training data by default.

### P11. Prepare truthful demonstrations and focused discovery

Owner: founder for publication, engineer for capability proof. Dependencies: current feature evidence and P08 findings. Preparation can precede demand validation; paid distribution cannot.

An initial permitted demo and small authorized organic recruitment post can precede the four-week cohort result once their own capability, privacy and capacity checks pass. Early observations improve subsequent assets. Broad distribution depends on recurring-value evidence; recruitment does not wait for customers who have not yet been recruited.

The first assets are one permitted source-to-insight-to-plan-to-PR demonstration, one already-implemented/no-fit example and one concise hosted tutorial. A labeled public fixture can demonstrate the workflow without revealing private sources or code. Customer examples require separate permission to publish the specific material and quote.

One recording is reused for several short posts and a tutorial. The initial SEO set covers the actual Instagram Saved export path, evidence-based video analysis and reviewing a tutorial against a repository. Each page has a distinct task, accurate limits, working action, canonical metadata and an update date. Bulk generic AI articles and unsupported platform promises are excluded.

The weekly research record updates the four foundational documents together when observations change the audience, offer or purchase argument. Negative results and objections stay visible. Owner ideas use [the existing review process](foundational/COPY-AND-IDEAS.md). Claims link to a current evidence record, and price/provider changes trigger a copy review.

Acceptance: a fresh prospect can explain what they receive, who it fits, the paid service's value and its funding limits after viewing the demo. Public materials pass a claim and privacy review. Organic distribution starts with one founder-authorized channel and expands from engaged use. No new social account, bulk outreach, public post or campaign is executed under this planning request.

## E. Expand only when the service earns it

### P12. Expand distribution and capacity

Owner: founder, with engineer operations evidence. Dependencies: recurring cohort use, real paid behavior, measured costs and support capacity.

Expansion is a specific experiment with an audience, asset, budget, measurement window and stop condition. Referral links or additional community/tutorial distribution can precede paid ads. Paid advertising needs a separately approved monetary cap and account. No platform subscription constitutes advertising authority.

Acceptance: customer acquisition cost uses actual spend and reconciled independent buyers. Return/usefulness and support burden do not deteriorate while intake grows. Capacity estimates include retry bursts, existing unknown holds, refunds and dated provider reviews. Unprofitable full-use behavior is not hidden by averages. If a limit is reached, admission or the affected processing route pauses; read-only access and account rights remain available when safe.

### P13. Make the V2 decision separately

Owner: founder. Dependencies: demonstrated recurring V1 value and maintainable operations.

The decision records what users repeatedly need beyond improving existing projects, whether they pay for it, its maintenance burden and the new permissions/spending risks. Candidate V2 work follows [the separate roadmap](V2-ROADMAP.md), starting with reviewable opportunity research and proposals before account provisioning, deployment or marketing automation.

Acceptance: a narrow V2 experiment has a specification, customer-owned account boundaries, licence review, explicit funding, failure/rollback plan and separate approval. Generating more repositories is not its success measure. V1 remains useful and maintained regardless of the decision.

## Measurement definitions and decision cadence

The weekly product report separates these measures:

| Measure              | Definition                                                                                         | Interpretation                                                                                         |
| -------------------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Independent setup    | Completed real setup and analysis without founder intervention                                     | Public-source usability; assistance and failures remain counted                                        |
| Library activation   | New user opens a completed source analysis                                                         | A first result, not willingness to pay                                                                 |
| Repeat value         | Activated user returns in a later week and explicitly reports a useful insight or project decision | Main early product signal; no positive judgment inferred from inactivity                               |
| Project activation   | Recorded relevance review plus a saved plan, manual handoff or documented no-action decision       | Distinct from running code or merging a PR                                                             |
| End-to-end retrieval | Imported eligible links yielding usable retrieved media                                            | Private, deleted, blocked and unsupported counts remain in the import report                           |
| Analysis completion  | Attempted processing yielding a usable analysis                                                    | The [evaluation specification](FEEDBACK-AND-EVALUATION.md) denominator remains separate from retrieval |
| Paid conversion      | Independent reconciled buyers divided by the eligible observed cohort                              | Window, sample size, annual/weekly/monthly interval and trial status remain visible                    |
| Cost and margin      | Actual provider/payment costs plus disclosed allocations against net revenue                       | Gross usage, credits, cash spend, contribution margin and owner-defined operating margin stay separate |

PostHog [funnels](https://posthog.com/docs/product-analytics/funnels) and [retention](https://posthog.com/docs/product-analytics/retention) support the hosted measurements where consent permits. Non-consenting participants can voluntarily supply feedback; analytics coverage and missingness are reported. The event system never captures private evidence to make a marketing metric easier.

A weekly 30-minute founder/engineer review examines failures, return behavior, usefulness, actual costs and one proposed change. The record identifies the decision, owner, evidence and next check date. This cadence is proposed; no recurring automation is created by the plan.

## Budget, release and support rules

The current EUR 10 inference pilot ceiling, service budgets and reservations remain hard bounds. Cohort size follows capacity, not an arbitrary growth target. No purchase, quota expansion or price change is assumed. Provider-invoice delays and human annotation delays remain external dependencies with independent work available.

Fixed Basic Vercel builds and normal queued concurrency remain selected. Documentation-only commits skip unnecessary deployments. Product changes receive focused tests, relevant native verification, secret/audit checks and exact version records. Existing critical tenant, source-deletion, execution, approval, payment and budget checks remain release blockers.

Provider tariff review is due before October 17; the security mitigation review is due before November 2. Country evidence follows its documented freshness window, and worker images are checked against actual expiry. Exact current runbooks control these dates; the six-week plan cannot defer a nearer operational expiry.

Public-source support initially covers one tested installation path and version matrix. Hosted support includes a monitored route, status/retry guidance, cancellation/export instructions and incident escalation. No 24-hour staffed support, uptime guarantee or fully local computation is promised without evidence and operating capacity.

## Owner decisions before implementation

The recommendation is to retain the developer/founder positioning for the first cohort and authorize one personal deployment path as follow-on work. Those are proposed decisions, not changes already made to D16 or the product brief. Cohort recruitment, public marketing, external account actions and any extra budget need their applicable authorization when concrete materials or forecasts exist. Existing policy approval and qualitative video reviews are not requested again.

The immediate execution order, once authorized, is P04 documentation audit, P01 annotation preparation, P02 cost reconciliation and P03 recovery design. P05 scope and P07 event audit follow. Features in P10 wait for an observed problem. See [the plan review](POST-V1-PLAN-REVIEW.md) for checks, corrections and unresolved dependencies.
